What PlantPulse does
Imagine a manufacturing plant with hundreds or thousands of machines.
Each machine produces readings such as:
{
  "machine_id": "compressor-104",
  "site_id": "plant-atlanta-01",
  "timestamp": "2026-07-28T13:30:00Z",
  "temperature_c": 92.4,
  "pressure_psi": 147.8,
  "vibration_mm_s": 8.2,
  "status": "running"
}
Your platform:
Generates simulated equipment telemetry.
Sends events through Kafka.
Processes them with Python services.
Detects abnormal equipment or processing conditions.
Stores current and historical machine health.
Exposes APIs for querying plant status.
Runs on Kubernetes.
Monitors infrastructure and application reliability.
Automatically responds to selected operational problems.
Demonstrates disaster recovery across cloud providers.

The seven parts that would make it impressive
1. A genuine distributed application
The project needs meaningful software, not only infrastructure configuration.
Build at least four Python components:
Equipment simulator
Generates telemetry from hundreds of simulated devices.
It should support:
Configurable event rates
Normal and abnormal operating modes
Sudden temperature spikes
Gradually increasing vibration
Malformed messages
Offline equipment
Duplicate and out-of-order events
Network delays
Validation and ingestion service
Consumes raw Kafka events and:
Validates schemas
Rejects invalid events
Adds metadata
Detects duplicates
Sends poison messages to a dead-letter topic
Exposes Prometheus metrics
Health-processing service
Calculates equipment health from recent readings.
You do not need a sophisticated machine-learning model. Transparent rules are sufficient:
if temperature > 90 and vibration > 7:
    severity = "critical"
elif temperature > 80 or vibration > 5:
    severity = "warning"
else:
    severity = "normal"
The SRE value comes from making this service reliable under high traffic and failures, not from producing the most advanced prediction algorithm.
Reliability controller
This is the project’s most impressive software component.
Write a Python service that watches operational metrics and takes guarded actions. For example:
Scale workers when Kafka consumer lag remains high.
Stop retrying poison messages and route them to a dead-letter topic.
Open an incident when error rates exceed an SLO threshold.
Roll back a deployment after repeated health-check failures.
Disable remediation after a maximum number of attempts.
Record every automated action in an audit log.
This turns the project from “I know DevOps tools” into:
“I write software that operates and protects distributed production systems.”
That distinction matters for an SRE Software Engineer position.

Define what “reliable” means before building dashboards.
Create service-level indicators and objectives such as:

Then create an error-budget document.
For example:

Your system should calculate:

Failed requests
Total requests

Why this matters
A typical candidate says:
“I installed Prometheus and created Grafana dashboards.”
A stronger candidate says:
“I defined measurable SLOs, created burn-rate alerts and tested whether the system met its availability and latency targets.”

For example:
Readiness probe
Prevents Kubernetes from sending traffic to a service before it can successfully connect to Kafka and its database.
Liveness probe
Restarts a service that is running but permanently stuck.
Pod disruption budget
Prevents too many ingestion-service replicas from being unavailable during maintenance.
Resource limits
Protect the cluster from a runaway service while preventing excessive throttling.
Horizontal autoscaling
Scales workers based on CPU or, more impressively, Kafka consumer lag through a custom metric.

5. Failure injection and incident response
This is where the project becomes an SRE project rather than a deployment project.
Create repeatable failure experiments.
Experiment 1: Kill an ingestion pod
Expected result:
Kubernetes replaces it.
Remaining replicas continue processing.
The availability SLO remains intact.
Kafka retains unprocessed events.
Processing catches up after recovery.
Experiment 2: Generate a Kafka backlog
Increase the telemetry rate from 100 to 2,000 events per second.
Expected result:
Consumer lag alert fires.
Horizontal autoscaling increases worker replicas.
Lag returns below the threshold.
Replicas later scale down safely.
Experiment 3: Deploy broken code
Deploy a version whose health endpoint fails.
Expected result:
Readiness checks prevent traffic from reaching it.
CI/CD smoke tests fail.
The deployment automatically rolls back.
An incident record is created.
Experiment 4: Introduce malformed events
Expected result:
Valid events continue processing.
Invalid events move to the dead-letter topic.
No infinite retry loop develops.
An alert fires if the dead-letter rate becomes abnormal.
Experiment 5: Add database latency
Expected result:
API latency increases.
Prometheus identifies the database dependency as the bottleneck.
Circuit-breaker or timeout logic prevents request pileups.
The system recovers after the latency is removed.
Experiment 6: Simulate a cloud outage
Expected result:
Backups are restored to the recovery environment.
Services launch in the secondary cloud.
A documented recovery-time objective is measured.
For every experiment, record:
Detection time
Alert time
Mitigation time
Recovery time
Data loss, if any
Root cause
Preventive improvement
6. Multi-cloud design without pretending to run everything globally
Do not spend thousands of dollars operating full production clusters in three clouds.
Use a credible strategy:
Azure: primary environment
Deploy the complete system to:
AKS
Azure Container Registry
Azure Database for PostgreSQL
Azure Blob Storage
Azure networking and identity services
GCP: disaster-recovery environment
Create a smaller standby deployment using:
GKE
Artifact Registry
Cloud SQL
Cloud Storage
GCP IAM
Demonstrate that the same Helm charts deploy to both AKS and GKE.
Alibaba Cloud: portability layer
Create:
Terraform module or documented deployment configuration for ACK
OSS backup configuration
RAM role design
Container Registry configuration
Provider-specific variables
A small temporary deployment is preferable, but a tested infrastructure module and detailed architecture are still useful when cost or account availability limits a full environment.
What makes this impressive
You are not claiming:
“I know every service in three clouds.”
You are demonstrating:
“I understand portable cloud architecture, while recognizing the identity, networking, storage and managed-service differences between providers.”
That is a much more defensible interview answer.

Where Ansible belongs
Kubernetes and cloud resources do not naturally require Ansible for everything, so do not force it into the wrong place.
Use Ansible for an on-premises plant edge environment.
Provision two or three Linux VMs that represent industrial-site gateway machines. Ansible should:
Create service users
Install Docker or required packages
Configure system limits
Install the equipment simulator
Configure TLS certificates
Install a metrics agent
Configure log rotation
Install and configure an NGINX reverse proxy
Start systemd services
Apply security hardening
Perform rolling updates
That creates a credible hybrid-cloud story:
Factory/on-premise edge
        |
        | Kafka-compatible secured connection
        v
Cloud Kubernetes platform
This is significantly more appropriate for Honeywell than using Ansible to install a random web server with no connection to the project.
